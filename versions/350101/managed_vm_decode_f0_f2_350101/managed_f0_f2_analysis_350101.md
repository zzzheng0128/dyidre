# 350.101 managed F0 / F1 / F2 analysis

## Scope and evidence

These are the **sign-module** programs stored at globals `+0x2c58d0`,
`+0x2c58d8`, and `+0x2c58e0`.  They must not be confused with HTTP-module
programs that are also called F0/F1.

The three bodies were dumped after `libmetasec_ml.so` initialization with the
local 350.101 unidbg harness, then decoded as 24-byte managed-VM records.
The dump manifest is in
`unidbg-android/target/managed_program_dumps_350101_f0_f1_f2_20260904/summary.md`.
All records are known to the current interpreter table: F0 30/30, F1 30/30,
F2 26/26.  There is no `UNKNOWN_OP` in this set.

| program | descriptor | runtime body | records | conclusion |
|---|---:|---:|---:|---|
| F0 | `0x1277e5c0` | `0x1268dc00..0x1268ded0` | 30 | CF00 setup + CF01 transform adapter |
| F1 | `0x1277e600` | `0x1268df00..0x1268e1d0` | 30 | CF00 setup + CF02 transform adapter |
| F2 | `0x1277e640` | `0x12369500..0x12369770` | 26 | alternating byte-wise 32-bit mixer |

F2's runtime code is mapped at `0x12369500`, which is `-0x16b00` from this
run's SO load base (`0x12380000`).  Therefore its generated filename's
`0xfffffffffffe9500` is a signed runtime-relative offset, not an invalid
decode or a static SO address.  It was initialized/unpacked into a neighboring
runtime mapping.

## F0 and F1

F0 and F1 have the same stack save/restore and null guards:

```text
if (S4 == 0 || S6 == 0)
    return;
```

On the success path they preserve the original arguments as:

```text
source      = S4
destination = S5
auxiliary   = S6
```

They invoke CF00 after programming the call slots as:

```text
S4 = destination
S5 = *(int32_t *)(source + 0x0c)
S6 = 0x20
CALL CF00
```

`managed_cf_semantics_350101.md` identifies CF00 (`0x16ea70`) as the
`sub_10BFD8(slot4, low32 slot5 length, low8 slot6 fill-byte)` make/fill
MEM_BLOCK helper. Thus F0/F1 create a destination whose length comes from
`source+0x0c`, filled with byte `0x20`; the exact interpretation of that
input field remains owned by CF00 rather than the managed layer.

Both then make the same five-slot transform call:

```text
S4 = *(uint64_t *)(destination + 0x10)  // output data
S5 = *(uint64_t *)(source      + 0x10)  // first input data
S6 = *( int32_t *)(source      + 0x0c)  // first input length/value
S7 = *(uint64_t *)(auxiliary   + 0x10)  // second input data
S8 = *( int32_t *)(auxiliary   + 0x0c)  // second input length/value
```

The terminal binding is the only semantic difference:

| program | terminal call | native entry | current evidence-backed name |
|---|---|---:|---|
| F0 | `CALL_CF_INDEX 0x01` | `0x16eac0` | `flattenedTransform_CF01_350` |
| F1 | `CALL_CF_INDEX 0x02` | `0x16eb40` | `flattenedTransform_CF02_350` |

F0/F1 return via the usual VM `S31` return address and do not write a
conventional `S2` result.  Their visible result is the destination object
passed in original `S5`.

## F2

F2 takes `S4` as a byte pointer and the signed 32-bit low portion of `S5` as
the byte count.  It resets `S2` to zero, treats a non-positive count as an
empty input, and leaves the final state in `S2` (sign-extended from 32 bits).

```c
uint32_t state = 0;
for (uint32_t i = 0; i != (uint32_t)count; ++i) {
    uint32_t byte = bytes[i];
    uint32_t old = state;
    if ((i & 1) == 0)
        state = byte ^ old ^ (old << 7) ^ (old >> 3);
    else
        state = ~(((old << 11) | byte) ^ (old >> 5) ^ old);
}
S2 = (int32_t)state;
```

This conclusion comes directly from records `0006..0018`: the parity branch
is at `0007`, the even update at `0008..000d`, the odd update at
`000f..0015`, and the loop back-edge at `0018 -> 0006`.  It is appropriate to
call this a custom alternating mixer, not a named checksum, until a caller or
test vector establishes its intended role.

## Artifacts

- `F*_*.decoded.asm`: instruction-level source of truth.
- `F*_*.linear.c`: mechanical lifts generated by the decoder.
- `managed_f0_f2_recovered_350101.c`: structured lift of the conclusions
  above; CF calls deliberately remain external.

The next useful step, if the native algorithms behind F0/F1 are needed, is to
lift the two flattened native bodies at `0x16b748` (CF01) and `0x16beb0`
(CF02). F0/F1 themselves are now fully accounted for at the managed layer.
Until those lifts close, the managed runtime exposes only explicit, independent
raw-buffer provider bridges for F0/CF01 and F1/CF02: each receives initial
destination bytes, source/auxiliary bytes and raw low-32-bit lengths, and must
return exactly the source-length output for atomic writeback. Neither bridge
claims its provider implements the flattened native body, and one never
substitutes for the other.
