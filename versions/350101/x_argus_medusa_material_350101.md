This C file is the current "de-VM" working form for the high-value managed CF
helpers. It lifts slot access, CF61 SM3, CF48/CF49 short-header pack,
CF44 base64, CF98 key/value output, CF100 short plaintext formatting, and CF79
Medusa JSON-number writes. It intentionally leaves the shared flattened
micro-blocks as `flattened_*` placeholders until their table-index CFG is
recovered.

## X-Argus material

Observed `F5` flow:

1. `CF61(slot4=url_query, slot5=0x2c0, slot6=state)` digests/transforms the
   query string.
2. `CF38(..., src=state, len=0x20)` snapshots the first 0x20-byte transform
   output.
3. `CF61(slot4=x_ss_stub_body, slot5=0x10, slot6=state)` mixes the 16-byte
   `x-ss-stub`.
4. Additional `CF10/CF38` copies assemble multiple 0x20/0x10/0x04 fragments.
5. `CF61(slot4=packed_material, slot5=0x44, slot6=state)` transforms a 0x44
   intermediate pack.
6. `CF44(slot4=out_ref, slot5=input_mem)` base64-encodes an input MEM_BLOCK
   with `src_len=0xc2`.
7. Two `CF98("%s")` calls write generated `char **out_key` and `char **out_val`
   back to the outer stack.
8. Outer code copies those strings into `MEM_BLOCK`s and inserts
   `X-Argus` through `treeMapPut_X22_X27_X28_350` at origin `0x14A3A0`.

## X-Ladon material

Observed `F7` flow:

1. Short pack contains `derived_block="1128"` and
   `stack_memblock="1588093228"`.
2. `CF100` receives format string `%u-%s-%s`, seed `0x6a945fad`, and two
   string-like arguments.
   In the post-return run the formatted MEM_BLOCK is:

   ```text
   1788108717-1588093228-1128
   ```

3. `CF38*2` snapshots two 4-byte chunks from the formatted/derived result.
4. `CF48` takes:
   - `slot4`: formatted short plaintext, len `0x1a`, e.g.
     `1788108717-1588093228-1128`;
   - `slot5`: a 4-byte scratch/prefix MEM_BLOCK before the call;
   - `slot6`: a 32-byte ASCII hex-like key/material.
   It rewrites `slot5` into a 32-byte binary transform result. Its lower helper
   `0x16CCD8` enters the shared flatten dispatch table `0x29F420`, so the exact
   algorithm name is still deliberately left open.
5. `CF49` appends/cats the 32-byte transformed block onto the 4-byte prefix,
   producing a `0x24` byte binary pack.
6. `CF44` base64-encodes that `0x24` byte binary pack into the final 48-char
   `X-Ladon` value.
7. Two `CF98("%s")` calls return key/value to the outer stack.

## X-Medusa material

`F8` is the large final managed-sign stage. It reuses the full pack from `F5`
with `final_flag=1`.

Observed `F8` flow:

1. `CF61(slot4=url_query, slot5=0x2c0, slot6=state)` digests/transforms the
   same query material as Argus.
2. Early `CF07` copies fold in the 0x20 digest, the 0x10 `x_ss_stub`, and a
   4-byte seed/version-like fragment.
3. `CF79` writes eight JSON numeric fields:
   `cmr`, `cmr2`, `un_h`, `vpn`, `kd`, `fkd`, `pd`, `do`.
   The numeric value comes from `managedFrameGetSlotDouble_350(slot2)`, which
   reads the double-slot view at `frame->buf+0x82e0+slot*8`, not the generic
   qword slot table.
4. `CF38*3` snapshots two 0x10 chunks and one 0x04 chunk.
5. `CF61(slot4=packed_material, slot5=0x44, slot6=state)` transforms another
   0x44 intermediate pack.
6. A long `CF07` block assembles the final Medusa binary. The latest raw-CF07
   focused run proves the final `CF44` input can be reconstructed byte-for-byte
   from those copies.
7. `CF44` base64-encodes the final binary pack. Current observed input lengths
   are `0x2c4/0x2c8`; the latest byte-exact run is `0x2c8`.
8. Two `CF98("%s")` calls return key/value to the outer stack.
9. Outer code inserts `X-Medusa` by direct `treeMapPut_350` near `0x14A53C`.


Both work areas differ from the bytes later copied into the final pack, so F8 is
not pure memcpy. A middle VM/native-helper section mutates those work areas
before the final `CF07 -> CF44 -> CF98` output chain. The follow-up
write-watch report has pinned this down more precisely:

```text
mini work area:
  F8 main interp0=0x310000010d7
  ST8 writer 0x157EE4
  records 0xcbc/0xcc2/0xcc7/0xccd, 20 byte writes

large subpack prefix:
  nested F12 interp0=0x800001245f
  ST64 writer 0x157EB0
  record 0x82, 31 qword writes, covers sub+0x000..sub+0x0f7
```

F12 不是拿 `sub[0]` 自己滚动变换，而是用另一个 source byte stream 对
sub-work 的 qword 做 bit-patch。当前大长度路径的参数形状是：

```text
s4 = dst_base/sub-work
s5 = dst_limit=0x2af
s6 = source byte stream
s7 = count=31
phase = 0 for all observed stores
```

由 31 次 `ST64` 的 old/new qword 可唯一反推这次的 source stream：

```text
b1 58 6e 0f f7 2c f9 36 18 b1 c3 4c 92 b5 e1 24
c5 ea 12 ca 3d 0e f6 1c bb e6 e7 ff 9e fc df
```

## What this means for reproduction

- `X-Gorgon`/`X-Khronos` are native pre-sign outputs from stage1/stage2.
- `X-Argus` is the `F5` managed program over query, stub, env/token pieces,
  digest fragments, and base64.
- `X-Ladon` is a compact `F7` managed program based on seed plus short pack.
- `X-Medusa` is the `F8` final managed program; it includes a larger
  environment/JSON collection and the final long binary pack before base64.
- `X-Helios` follows the same short-pack pattern as `X-Ladon`.
- `X-Soter` is a later direct insertion and should be tracked separately from
  the `F13` wrapper output.

For a newer SO, first align these stable pivots:

```text
native stage1/stage2 pack -> managed full pack F5/F8 -> managed short pack F7/F13
CF61 SM3 adapter          -> CF44 base64           -> CF98 output string writer
treeMapPut wrapper origin -> generated X-* key/value
```

Next restoration targets:

1. Optional IDA cleanup: beautify `0x16CCD8` table-index CFG for
   `shortHeaderTransform32_flattened_CF48_350`. Its runtime/oracle behavior is
   already byte-exact, so this is not blocking header restoration.
2. Continue structuring decoded F5/F8 managed bytecode into named binary-pack
   fields. The records themselves are already decoded with `unknown=0`; the
   remaining work is field naming / serialization boundary tracing, not opcode
   recovery. For F8, `CF79` has already identified
   `cmr/cmr2/un_h/vpn/kd/fkd/pd/do` as JSON/env number inputs; they are not
   plaintext u32/u64/double fields in the final `0x2c8` pack.
