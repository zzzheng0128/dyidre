这里的“完整过程”指研究阶段和证据流转，不表示算法已经完整或通用地还原。
本页是过程审计与资料导航，不包含签名复现配方、敏感材料、拦截配置或保护绕过步骤。

## 1. 本次整理的口径

本次只读检查既有文档中的文件引用，并核对本地文件元数据；未读取原始业务日志正文，
未重新采集、运行签名或算法测试，也未修改探针、运行时、样本或 IDA。
日志大小来自文件元数据，本次没有计算原始日志内容哈希。

清单覆盖 97 个选定路径：51 个当前存在，46 个在记录路径未找到；其中 81 个有文档引用，
4 个是配套文件，12 个仅作为现存关联记录列出。这些数字不是采集次数、有效样本数或覆盖率，
也不是工作区所有日志的总数。失败试跑、联网流程、崩溃与稳定性日志没有全部纳入主清单。

必须区分以下三个维度：

| 维度 | 本页如何记录 | 不能推出什么 |
|---|---|---|
| 文件是否存在 | 现存 / 记录路径未找到 / 历史路径迁移 | 现存不证明内容完整；未找到不证明已删除 |
| 为什么列入 | 文档引用 / 配套产物 / 仅现存关联记录 | 出现在文档或命令示例中，不自动证明成功采集或被实际消费 |
| 结论是否有效 | 历史报告记载 / 受限验证 / 推断 / 已废弃 | 不能把历史摘要当作本轮重新验证 |

沿用总台账的证据等级：S 为静态确认，D 为动态观测，V 为限定条件下的精确对照验证，
P 为推断或局部语义。本页对这些历史等级的引用，不构成一次新的 D 或 V。

## 2. 整个过程怎样推进

下列是研究逻辑顺序，不是精确完成时间轴；多个阶段曾并行或反复进行。
能够直接确认的一次验收时间是既有[算法验收报告](algorithm_validation_350101.md)
记载的 2026-08-31 09:47 Asia/Shanghai。文件名中的日期不能单独作为完成时间证据。

### 阶段一：先确定研究的是哪个样本

问题：不同目录、旧版资料、真机和仿真环境是否指向同一份样本？

先建立样本身份记录，再解释入口、结构和日志。已有材料是 ELF 身份信息、版本目录和
样本清单。这一步的产物是[样本身份报告](metasec_so_identity.md)与
[分析轨迹](analysis_trajectory_350101.md)，不是运行日志。

能确认的是资料适用范围，不能据同名库、相似版本号或旧版运行稳定就认定算法等价。
`01-douyin` 的旧实现比较仍属另一条静态参考线，没有被当成本版本的动态验证日志。

### 阶段二：建立入口和对象边界的初步模型

问题：哪些数据是参数、对象状态、临时空间或返回容器？

历史分析结合入口快照、运行读写观察和静态引用，逐步形成结构候选；仅有一次内存快照
不足以命名所有字段，旧版结构也只作为候选。关键真机证据是 wrapper entrydump，
对应的早期 unidbg 结构观察日志目前部分未找到。

产物包括[结构恢复过程](recovery_process_350101.md)、
[真机与仿真入口形态对照](real_vs_unidbg_entry_shape.md)、
[字段证据表](x0_evidence.md)及结构头文件。产物中的已确认字段与临时视图应分开理解。

### 阶段三：建立真机参考证据集

问题：真实运行时看到了什么，哪些观察属于同一次采集？

历史证据分为 GumTrace 指令轨迹、入口快照、JNI 回调、环境事件和入口事件。
这些记录的粒度不同：指令轨迹描述执行，快照描述一个时刻，回调日志描述边界事件，
控制台主要描述采集器是否正常运行。

产物是 `runs/350101/` 中的批次及归档原件。两份较大的 HTTP GumTrace 原件已迁入
`_archive/large_raw_traces/`，有[归档记录](../../docs/cleanup-manifest-20260831.md)。
采到某条路径只证明该次观察，不覆盖未触发分支、未出现的状态或其他版本。

### 阶段四：建立 unidbg 受控基线，并与真机比较

问题：输出或路径差异来自环境变化、输入不一致，还是实现差异？

历史过程使用固定环境重复运行，以及请求、环境、分支和指令序列对照。
比较必须记录输入条件和日志配对，不能只看到最终输出有差异就断言算法不同。

产物包括[确定性记录](deterministic_replay_350101.md)、
[真机环境同步记录](true_env_sync_350101_214509.md)与
[执行序列对照报告](instr_diff_350101/managed_blr_cf_target_diff_350101_req01_v2.md)。
较晚的环境和指令日志仍在，早期若干固定基线原件未找到。
unidbg 能调用原 SO 并完成某次运行，不等于已经独立恢复其所有算法。

### 阶段五：单独分析托管 VM

问题：程序如何组织、运行时上下文是什么、解码结果与实际观察是否相符？

历史分析结合静态程序记录、上下文日志和调用观察，形成解码结果、程序统计和语义说明。
`vmctx`、程序专项日志与工作区观察是这一层的证据，不能自动归入 native VMP。

产物是[托管 VM 恢复记录](managed_vm_recovery_350101.md)、各 `managed_vm_decode*/`
目录和[托管运行时说明](managed_vm_runtime_350101/README.md)。
能够解码某个程序不代表它的每个宿主依赖、异常路径和状态副作用都已经独立实现。

### 阶段六：整理 CF、F、G 及其证据边界

问题：编号对应什么角色，静态绑定和运行时语义之间还差多少证据？

CF 是模块范围内的宿主调用编号，F 是程序编号，G 是导入/绑定相关编号；不能把它们当作
一张跨模块、跨版本通用的函数表。历史 CF 入参、调用后状态和专项日志用于支持局部语义，
G 台账则还包含静态链接与引用证据。

产物是[CF 语义记录](managed_cf_semantics_350101.md)、
[G 绑定台账](g_binding_ledger_350101.md)和各模块的边界说明。
CF 的实现数量可能包含受限实现或外部提供器；G 的绑定闭合数量不等于业务对象语义全部明确。
因此这些计数不能解释成“签名算法恢复百分比”。

### 阶段七：独立处理 native VMP 的局部轨迹

问题：原生 VM 的入口事件、执行轨迹、字节码和解码产物怎样对应？

这一条证据线使用 GumTrace 局部轨迹、从主轨迹截出的片段，以及 stackplz/uprobe 入口事件。
入口事件只能支持调用出现过及相应关系，不能代替完整指令轨迹。

产物是[native VMP 台账](vm_generic_350101/README.md)、
[入口事件分析](vm_generic_350101/vmp_entry_analysis_process_350101.md)和局部解码/提升结果。
切片覆盖不是整个库的覆盖；字节码地址、片段中的函数入口、最外层采集入口不能混为一谈。
本页保留历史文件名作为检索标识，不将文件名中的数值扩展成新的拦截地址表。

### 阶段八：形成独立模块实现，并做限定范围的验收

问题：已提取的计算是否在指定向量和固定环境下与参考一致？

既有[算法验收报告](algorithm_validation_350101.md)分模块、输出级、固定环境实现和
原 SO 仿真对照记录结果。独立 C 验收的三份日志仍在，但其中引用的部分早期 unidbg 原件未找到。

报告支持“已有部分独立实现与固定环境一致性验证”，不支持“完整通用实现”。
当前[实现边界说明](c_recovery_suite_350101.md)仍指出环境状态和上层材料构造的限制；
其中“底层 API 入参”不能全部解释成必须外部采集的动态输入。

### 阶段九：把结论固化到台账、结构与 IDA 记录

问题：哪些结论足以命名、哪些仍须保留为候选？

历史过程将证据支持的结构、命名和关系写入文档、头文件与 IDA 更新记录，
同时保留推断和未闭合边界。结构视图、字节窗口和完整业务结构不是同义词。

产物是[总流程台账](so_runtime_flow_350101.md)、
[IDA 更新记录](ida_rename_update_350101_20260831.md)及结构文件。
静态上共用一个函数或对象，不足以证明环境检查状态被最终输出消费。
本次整理只索引这些历史产物，没有重新打开或修改 IDA。

### 阶段十：用后续 MS.b 场景日志补充环境证据

问题：不同运行场景下，回调类型、出现情况和状态依赖是否有变化？

`msb_long01` 的[历史差分报告](../../runs/350101/msb_trace/msb_long01/msb_diff.md)
明确对照的是旧 CF71 日志。后续冷启动和空闲批次有单独的
[场景地图](../../runs/350101/msb_trace/scenario_map_350101.md)。

这些属于后续补证，不能倒算成早期算法验收的覆盖。存在修正后的 unidbg 日志，
不代表旧差分报告已经针对它重新生成；日志条数、回调类别数也不等于完整动态材料已接入。

| `msb_diff.md`、指令差分报告 | 表达指定源文件之间的比较 | 对所有后续日志自动有效的结论 |
| 结构头文件、IDA 更新记录 | 固化证据支持的命名和结构 | 结构每个字段都已动态验证 |
| 编译输出、runner console、logcat | 记录构建、采集器或进程状态 | 算法正确、采集完整或线上行为一致 |

## 6. 几条最容易误读的证据关系

### 6.1 主轨迹、切片与解码不是三次验证

`gumtrace_1f7860_slice.log` 的原件是归档的 `gumtrace_getHttpHeadVerify_350.log`，
来源关系见[切片说明](exeVMInner_x_headers_350101.md)。后续解码汇编仍依赖同一原件。
如果原始采集遗漏某类行为，切片与解码不会补出新的动态覆盖。

### 6.2 旧路径与文件缺失是两种情况

`dyidre/vmp/vmp_entry_350101.log` 已有明确的新规范路径，不能称为原件丢失。
相反，不少早期 unidbg 日志只有文档引用和结果摘录，当前未找到原件。
此时可以保留“历史报告记载”的结论，但不能声称今天已经重读原始 trace 复核。
新跑出来的不同批次也不能无说明地充当旧原件。

### 6.3 文件存在与结论仍有效是两种情况

[后续差分报告](instr_diff_350101/managed_blr_cf_target_diff_350101_req01_v2.md)
明确废弃旧 `blrwin` 的 first-diff 判断。该日志应保留为历史记录，而不是删除事实或继续当当前基准。
JSON 中对此设置了 `assessment.status = superseded_conclusion`。

### 6.4 MS.b 旧差分不等于修正后重新验证

`msb_long01/msb_diff.md` 指向 `cf71_tls_20260904.log`，不能自动解释为对
`msb_after_fix.log` 或其他后续运行的结论。新场景日志也属于后续证据。
即便调用次数或部分返回摘要一致，仍不能替代完整值、调用上下文和状态生命周期的一致性证明。

### 6.5 有算法实现不等于材料生成和环境语义全部闭合

当前已有部分独立模块计算与固定环境复现。底层 API 的显式入参可能是外部输入、固定配置
或上游计算的中间值；仅凭参数名不能列出确定的“必须从真机取得”的材料清单。
固定数据包、外部提供器或配置覆盖也不能证明完整环境采集已经独立恢复。

## 7. 当前可以下的结论与仍缺的证据

可以下的结论：研究主线和主要产物已经有连续的文档记录，部分原始轨迹和验收输出仍在，
能区分静态关联、动态观察、局部实现和固定基线验收。

仍然不能夸大的部分：

1. 原始证据完整性：选定清单中有 46 个记录路径未找到；报告摘录不能替代原件。
2. 采集血缘：`latest` 路径、切片和摘要需要内容身份与父子关系，文件名本身不够。
3. 比较有效性：已废弃基准、旧差分报告和新运行必须分开。
4. 动态覆盖：未采集的分支、状态变化和调用上下文不能由一次内存快照补齐。
5. 实现完整性：CF/G 数量、能够解码程序或编译成功，不等于端到端算法完整。
6. 通用性：固定环境、当前版本的对照不证明跨设备、跨状态或跨版本兼容。

维护时遵守：
